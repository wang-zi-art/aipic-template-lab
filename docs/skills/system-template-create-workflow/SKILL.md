# 系统模板创建流程

给定一个明确的模板类型 `TPLxxxx`，依次使用下面三个项目 Skill。开始前读取 `mcp-test/CORE.md`；只为当前阶段读取所需资料，沿用同一模板已核对的 `manifest.json`、`sourceNote`、友商参考和当前会话中已确认的信息。资料或审批版本未变化时不重新整理全部历史。三个 Skill 各自负责专业内容，本文只规定交接、审批和推进条件。

1. [system-template-acceptance](../system-template-acceptance/SKILL.md)：生成并修订验收标准。
2. [system-template-prompt-candidates](../system-template-prompt-candidates/SKILL.md)：根据已批准标准生成并修订候选提示词。
3. [system-template-candidate-create](../system-template-candidate-create/SKILL.md)：通过项目 MCP 创建已批准候选，回读核实并更新本地登记。

## 第一阶段：验收标准审批

按第一个 Skill 读取指定模板资料，交付带 `AC-vN` 版本的**完整验收标准**及待确认事项，等待负责人明确表示通过。若反馈针对某些标准，只修改受影响的判断，并交付完整新版本；继续留在本阶段，直到当前版本获批。用户已在本轮或此前会话明确批准的同一版本可直接沿用，不重复请求审批。未批准时不得生成候选提示词。

## 第二阶段：候选提示词审批

将获批的 `AC-vN`、`sourceNote` 和友商参考交给第二个 Skill，交付 2 至 3 套完整候选及**一份创建配置交接**。供审批的内容须明确本次创建名单、共用的模型／分类／有序栏位配置／补充描述设置／展示素材，以及每个候选的版本、名称、简介、各栏完整模型作用和完整基础提示词。未另行指定时采用候选 Skill 中的测试默认值；已确认的模板专属设置优先。缺少会改变表单的信息时，在本阶段利用现有上下文和只读 MCP 核对，仍无法确定则集中请负责人补足，不留到远程写入后临时拟写。

等待负责人明确批准当前候选版本和创建名单。收到修改意见后针对受影响的候选修订，并重新交付该候选的完整新版及当前创建名单；已确认且未受影响的候选保留版本。若验收标准也改变，回到第一阶段确认新标准，再检查并修订受影响的候选。不得把沉默、初稿展示或局部赞同视为整批创建批准。

## 第三阶段：创建与报告

第二阶段的当前版本、创建名单和配置获批后，**直接**按第三个 Skill 执行一次整批预检和管理员环境核对，再逐项创建；MCP 内部逐项按准确版本完整回读，最后统一更新 `mcp-test/materials/<模板目录>/candidates.json` 与项目状态，不再另设创建许可。只创建获批名单中的候选，直接使用获批字段，不重新拟写名称、简介或上传要求。若此时后台模型、分类、栏位或现有候选状态与审批时不同，停止受影响项并报告具体差异；不要悄悄改用其他配置。创建结果不确定时按原执行编号核对，不自动重复创建。

最后逐项报告创建是否完成、后台模板与版本 ID、状态、执行编号及本地登记是否完成。`testing` 表示可试用，不表示已生图、验收通过或发布。

## 跨轮交接

每次交付或继续任务时保留一份简短状态：`TPL` 编号、当前阶段、已批准的 AC 版本、各候选当前版本与批准状态、拟创建名单、已确认的创建配置、未解决问题、下一动作。优先从当前会话和用户指定的研发记录恢复已批准内容；找不到完整文本或批准证据时先补齐，不凭版本号或旧报告猜测。两次人工确认分别发生在验收标准和候选配置交付之后；不能为了等待确认而提前写入后台，也不重复索取已给出的确认。
