# 系统模板提示词研发

本文是本项目模板提示词研发流程的唯一维护位置，供用户与助手按阶段协作使用。

版本：v0.1；更新日期：2026-09-20；状态：首版待负责人审核，尚未完成实际模板全流程验证。

## 背景、目标与分工

项目已进入打包发布与测试修改阶段，需要逐步准备一系列供用户使用的系统生图模板。每次只研发一个模板，以实际生成结果为依据，交付可填写到后台的每个图片栏模型作用说明和完整基础提示词。

用户提供同行小程序的功能说明、成组上传图与对应生成效果图，随后提供另外30组只有上传图的测试素材；用户负责实际生图测试、反馈和效果确认。助手负责参考分析、验收标准、候选提示词、结果对照、问题归类与优化。

同行素材用于理解功能和视觉目标。区分“说明中明确提出”“图片中实际观察到”“助手推测”，不声称还原了同行隐藏提示词，也不把同行精选效果图当成稳定性证据。

本技能只定义非代码研发流程。不会因使用本技能自动调用付费生图、修改业务代码、写入后台或发布模板。完成提示词交付后，发布按项目既有流程另行执行。

## 协作与记录规则

- 顺序固定为下述五步；根据反馈在当前步骤迭代，或回到受影响的前一步。只处理当前阶段，不在验收标准未确认时提前输出候选提示词。
- 用户已在会话中确认的内容直接沿用，不重复索要确认。用户提出修改不等于否定全部既有结论；只有明确改变的部分才调整。
- 材料不全时，先完成可确定的整理，并集中说明影响当前步骤的缺失项。图片不可见、配对不明或未提供时，不编造观察结果。
- 每轮简要记录：模板名称、当前步骤、验收标准版本、提示词版本、已确认结论、待补材料、下一步。后续继续时优先从这份阶段交接和受影响的实测证据接续；已确认且未变化的 30 组清单、旧轮全部结果和历史提示词不逐轮重读或重写，但最终覆盖统计仍纳入全部有效样本。
- 验收标准用 AC-v1、AC-v2 编号；候选用 A-v1、B-v1、C-v1；定稿用 Final-v1。每轮保留版本差异和对应实测记录，不能用新提示词解释旧版本结果。
- 单个模板的材料和结论保存在该模板的独立研发记录中，不把具体案例不断追加到本技能。用户未指定保存位置时先在会话交付，不自行把人物图片或未公开提示词加入代码仓库。

## 第一步：生成并反复确认验收标准

指定模板的验收标准由 [`system-template-acceptance`](../system-template-acceptance/SKILL.md) 单独处理：从正式素材档案的 `sourceNote` 和友商参考图提炼带依据的标准，交付初稿，按负责人反馈修订完整版本。负责人确认后记录标准版本，再进入第二步。测试次数、通过率和可接受缺陷由当前模板协作确定，不沿用历史建议作为默认门槛。

## 第二步：接收另外30组上传图

输入：另外30组只有上传图、没有生成效果的素材。每组是一次生成所需的全部栏位图片，不等同于单张图片，也不要求用户提前准备输出。

执行：

1. 编号 T01—T30，逐组核对栏位数量、图片顺序和可见内容；分批提供时累计清单，只列缺失或无法判断的部分。
2. 按已确认标准标注素材特征、可能难点和适用性，不能把“预期容易成功”写成“已测试通过”。
3. 检查是否重复、缺栏或明显偏离已确认范围。若大量日常素材不适用，指出验收范围与真实使用之间的冲突，交由用户调整；不为了提高通过率偷偷删除难样本。
4. 整理对比测试安排。可先使用部分代表样本探索，再覆盖其余样本；若建议保留部分素材用于后期验收，说明分配并由用户决定，不强制额外收集30组。

本步产出：30组素材清单，含组号、栏位对应、覆盖特征、疑问与建议用途。材料尚未齐全时不标记本步完成；用户明确调整数量或要求提前推进时按新范围执行并记录。

## 第三步：生成2至3个有明确差异的候选提示词

指定模板的候选设计由 [`system-template-prompt-candidates`](../system-template-prompt-candidates/SKILL.md) 单独处理：依据已确认的验收标准、正式素材档案和友商参考，交付 2 至 3 套有实质差异的完整图片栏模型作用与基础提示词，以及首轮测试建议。若第二步的测试素材尚未齐全，候选仍可作为待测试版本交付，并明确现有测试覆盖范围。

负责人明确要求将已确定的候选创建到后台时，另用 [`system-template-candidate-create`](../system-template-candidate-create/SKILL.md) 执行 MCP 创建和本地候选关联登记；交付候选文本本身不触发后台写入。

## 第四步：用户测试，筛选主选与备选

用户执行真实生图并反馈。助手按标准比较结果，提出修改或重新生成候选，直到用户确认一个满意的主选和一个有测试依据的备选。

建议每轮反馈至少能对应：样本组号、候选版本、模型与关键设置、结果图、用户意见。只提供文字反馈时先依据描述分析，明确尚未看到的细节；需要视觉判断的问题再请求对应原图和结果，不要求用户重传已经可用的材料。

比较规则：

- 同一轮候选尽量使用相同输入与配置，每次从原始输入独立生成；多轮修图后的效果不能当作一次生成结果。
- 收集本轮全部结果。批量输出逐张评分，不只保留最好的一张；重复生成次数与不同输入组数分别报告。
- 按标准编号记录合格项和问题，再作整体分级。有完整数量才计算通过率，不从几张精选反馈推算整体可靠性。
- 将超时、无图等执行失败与出图后的质量问题分开记录；需要统计整体可用率时保留全部尝试作为分母。
- 若总体方向正确，局部修改并输出完整新版；若候选思路本身不适合，回第三步生成新候选；若目标发生变化，回第一步更新标准。
- 主选和备选分别保存版本、完整文本、适用条件、测试表现与缺点。未实测的候选只能称为“待测备选”。

本步结束依据用户实际测试和已确认的判定规则。助手可以提出主选建议，不自行宣布用户满意。

## 第五步：归类问题，持续优化为最终提示词

输入：主选、备选、所有已有测试反馈与验收标准。

将问题整理为“样本与结果 → 标准编号 → 问题表现 → 可能原因 → 修改假设 → 复测结果”。按模板实际情况区分主体一致性、参考图作用混淆、构图、光影融合、细节结构、风格偏差、补充描述冲突、输入条件和模型能力问题；原因未验证时标明假设。

每轮处理：

1. 优先解决硬性失败和重复出现的问题，选择一个主要修改假设，控制改动范围。
2. 给出修改理由、预期影响及包含所有栏位作用和基础提示词的完整新版。
3. 用户复测此前失败样本与此前成功样本，检查改善与退步；逐步覆盖30组输入及声明支持的关键使用条件。
4. 对重要样本安排重复独立生成，以检查随机失败；次数依据已确认计划或用户本轮安排，不自行触发付费调用。
5. 若同一问题连续三轮有实测反馈的修改仍未改善，停止重复堆词，整理已尝试方向、证据与限制，讨论回第三步、更换方法或调整适用范围；不能偷偷降低验收标准。

如果30组全部参与过调词，明确其结果属于开发素材复测，不能称为独立新素材验收。可建议补充新素材，但不另加用户未要求的强制第六阶段，也不承诺未经验证的泛化能力。

结束时依据第一步的结束条件和用户最终反馈交付：

- 模板名称、最终提示词版本、对应验收标准版本。
- 按顺序列出的每个图片栏名称与完整模型作用说明。
- 可直接填写后台的完整基础提示词。
- 与模型、比例、分辨率、质量及用户补充描述相关的适用条件。
- 实测覆盖范围、关键问题处理结果、未解决限制；备选保留原版本和证据，主选改善不自动证明备选同步改善。
- 明确结论：证据不足时标记“定稿候选，待实测确认”；实际满足约定标准且用户确认后标记“提示词研发完成，可交付上线配置”。这不表示后台已经发布。

## 后续修改本技能

用户明确要求调整流程时，直接修改本文，更新版本、日期和受影响的阶段；在交付说明中概括变化。区分适用于所有模板的新规则与单个模板的特殊要求，后者保留在该模板研发记录中。

流程变化时保留已确认且仍适用的标准与实测证据，只重做受影响的步骤。修改技能本身不等于任何模板已经重新验收。

本文件保存在独立项目的文档目录，不代表已经安装到全局技能目录。可按本项目中文索引选择，或在会话中指定本文件路径；不维护第二份安装副本。
